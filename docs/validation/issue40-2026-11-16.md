## Native ADBC surface audited

The live Rust test uses the engine's `dbt-adbc` driver manager and Redis auth
mapping, not the Python adapter or SQL replay. It loads ABI **1.1.0** and checks:

| API/behavior | Evidence |
| --- | --- |
| Driver/database/connection initialization, URI/credentials/TLS options | Live Rust audit and native builds |
| Driver ADBC version metadata | `Database::adbc_version` reports V110 |
| Statement allocation, SQL execution and affected rows | Native smoke/parity/taxi and live audit |
| Prepare and Arrow record-batch binding | Bound INSERT succeeds and affects one row |
| Arrow stream binding and bulk ingestion | Two-row append succeeds and affects two rows; Python/CSV paths exercise separate client ingestion |
| Catalog/schema/table/column metadata and table schema | `GetObjects` and `GetTableSchema` exercised; native docs/catalog passes |
| Schema-only query and empty result stream | `StatementExecuteSchema` and zero-row read pass |
| Reuse, errors and concurrency | Four distinct connections use identically named temporary tables, recover after a missing-table error, and read the shared three-row table |
| Ownership and cleanup | Result readers/statements scoped and dropped; temporary tables are connection-local; owned audit and project schemas removed |

The engine's seed path uses SQL literals; Python/CSV ingestion is a separate
Arrow runtime. Transactions/rollback, Substrait, distributed partition APIs, HA,
multi-replica Flight routing, and an active cancellation stress test are not
qualified by this audit. Static analysis remains disabled for Redis.

## Concrete failures found and fixed in the candidate

- [#58](https://github.com/redis/redis-dbt-adapter/issues/58): Flight requests
  failed with `session is busy` and statement-close warnings when schema probes,
  debug queries, hooks or limited reads left Arrow streams open. Schema probes
  now use the schema API; SQL headers retain their session effects; unread
  result batches are discarded before the next RPC and statements are closed.
- [#59](https://github.com/redis/redis-dbt-adapter/issues/59): concurrent native
  model builds, Flight materializations and Python CSV ingestion surfaced
  explicit refused snapshot publications. Bounded retries recognize the exact
  native/wire failure, preserve statement boundaries and reusable input, and
  refuse cancellation or unknown outcomes.
- [#60](https://github.com/redis/redis-dbt-adapter/issues/60): taxi unit-test schema
  inference rejected `Decimal256(76,16)` via the PostgreSQL formatter. Redis now
  retains decimal precision/scale/nullability without widening PostgreSQL types.
- [#61](https://github.com/redis/redis-dbt-adapter/issues/61): parity parsing
  rejected duplicate `driver_options`; TLS trust and streaming now share a mapping.
- [#62](https://github.com/redis/redis-dbt-adapter/issues/62): a decimal-valued
  aggregate failed a Jinja integer comparison with “expected 4, got 4.” The
  known integer-total queries now cast explicitly to BIGINT, without floating
  point comparison or dropping the stable-row-number checks.

## Reproduction and retained evidence

Provision the disposable [Enterprise fixture](../../scripts/README.md), source
its private environment, and follow the [Flight qualification commands](../../scripts/README.md#flight-sql-qualification).
Build the Flight server with `scripts/build_flight_server.py`; retain its JSON
manifest and the security/functional JUnit summaries. The full local Flight
suite ran with `-n 4` and `REDIS_ADBC_TRANSPORT=flightsql`.

Build the pinned engine from [the v2 guide](../../v2/README.md), install the
separate optional runtime, and run:

```sh
# Source the verified Enterprise env.sh first. These commands create random
# schemas and remove only the namespaces they own.
export RUST_LOG=trace
python3 v2/smoke.py --dbt /path/to/redis-enabled-dbt --build
python3 v2/parity.py --dbt /path/to/redis-enabled-dbt --keep-artifacts
python3 v2/taxi.py --dbt /path/to/redis-enabled-dbt \
  --csv /path/to/yellow_tripdata_2019-01.csv.gz --keep-artifacts
# From the engine checkout, using the same verified environment:
cargo test -p dbt-adapter-engine --test redis_adbc -- --ignored
```

The native manual workflow now resolves the driver release once and records
that selection, engine/integration source commits, binary identity and
`Cargo.lock` as run artifacts. The Flight workflow retains its resolved build
manifest and JUnit summaries. The committed JSON here is the sanitized local
summary; private temporary logs are diagnostic material, not public evidence.

## Remaining boundaries and follow-ups

The native adapter contribution is [dbt-labs/dbt#17195](https://github.com/dbt-labs/dbt/pull/17195).
It is submitted, not merged. [#63](https://github.com/redis/redis-dbt-adapter/issues/63)

tracks the contributor CLA and maintainer-only fork-CI approval. Local tests do
not satisfy those upstream gates or add Redis to the stock dbt v2 executable.

[Issue #51](https://github.com/redis/redis-dbt-adapter/issues/51) tracks native v2
Flight SQL. Actual probes on this candidate reject `transport: flightsql` as
`Unsupported Redis profile option`; substituting a `grpc+tls://` URI without
that field fails with `Redis URI must use redis:// or rediss:// with a host`.
Both fail before a Flight query. Native v2 Flight SQL remains unsupported.

The v1 Flight qualification targets one authenticated, session-enabled public
server process on macOS. It does not establish other Flight databases, every
client/server version, Windows, multireplica deployments, or the full v1 taxi
dataset over Flight. This record adds scoped evidence; it does not erase the
older unauthenticated-run limitations or equate SQL replay with dbt integration.
