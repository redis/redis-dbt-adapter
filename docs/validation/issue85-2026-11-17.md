# Publication proxy SSL diagnostics: November 17, 2026

[Issue #85](https://github.com/redis/redis-dbt-adapter/issues/85) reports a
single intermittent `SSLError` during Flight qualification. That run recorded
only the exception class. Its SSL reason and cause cannot be recovered from
that observation, and it is not evidence of a benign peer close.

The proxy now retains qualification phase at detection, handler stage, exception
class, SSL library/reason identifiers and numeric SSL error code. Identifiers
are bounded to 80 uppercase ASCII letters, digits or underscores, starting with
a letter. Missing identifiers become null; invalid identifiers become `UNKNOWN`.
Neither exception messages nor RESP arguments/replies are copied into diagnostics.

The qualifier stores these records in `qualification.json` even when another
check fails. Errors remain fatal. It checks again after same-session
cancellation and after stopping the server and joining the proxy's handlers.
This closes a gap where errors after the refusal check could previously escape
the aggregate result. An earlier assertion failure is preserved if teardown
also records errors. No SSL exception was reclassified as an expected close.

## Validation environment

- macOS arm64, Python 3.13.16 with OpenSSL 3.5.9 for live runs.
- Engine `e9af305e318c086039ca39763b220f521e717490` (the issue #83 decimal fix),
  dbt-oss 2.0.11.
- Flight source `e4dcbd37322536f73ef923e0ab4b76a1abf3d4dc`.
- Latest stable Redis ADBC v0.0.28, resolved independently by each complete
  qualification to `b63a010d88d2b69707594cb9dc063992dac06b32`.
- Dedicated Redis 8.8.0 backend, verified TLS/auth, three shards, active 4x QPF,
  six Search workers, mnp/32 routing and 2 GiB database memory.

Each complete run starts a fresh server and TLS publication proxy, rebuilds the
Flight binary, creates fresh owned schemas, and runs security/native SIGINT,
smoke, parity/Python/CSV, Rust protocol, all seven refusal assertions and
same-session cancellation/resource checks. The backend is reused between runs;
"cold" here refers to server/proxy/client processes, not a Redis restart.
The tested proxy and qualifier source digests are retained with the results.
The branch builds on the issue #83 integration pin; its decimal fix is a
prerequisite for this qualification, not part of the proxy change.

An initial attempt before recreating the dedicated backend failed the
authentication availability probe because that backend had been removed after
prior validation. It recorded no proxy SSL error and is excluded from the
complete-run count. No assertion or TLS verification was relaxed to recover.

## Results and limits

- All **59 unit tests passed** on Python 3.13.16/OpenSSL 3.5.9 and
  Python 3.15.2/OpenSSL 4.1.0.
- All **four complete cold qualifications passed**, each including all seven
  refusal assertions, the native SIGINT probe, same-session cancellation and
  the final proxy check. Every `proxy_errors` array was empty.
- All **30 additional cold cancellation/resource probes passed**, each using
  a fresh Flight server process, proxy and client connection with the binary
  built by the first successful qualification. All proxy error receipts were
  empty; each probe observed an active lease, received cancellation, preserved
  same-session settings/data and drained newly active leases to zero.

The [machine-readable summary](issue85-2026-11-17/results.json) records source,
binary, lockfile, log and original receipt hashes, resolved dependencies, check
results and safe cancellation receipts. Live qualification exercised the working
proxy/qualifier changes over integration base `3e56bc2`; source digests, rather
than that base commit alone, identify the tested changes.

Unit regressions exercise actual loopback TLS on both proxy hops, including
untrusted frontend/backend certificates and corrupted application records.
They also exercise normal close, reason-less SSL failures, unclean SSL EOF,
credential-bearing exception text, phase/stage retention, cancellation and
shutdown failures, and preservation of an earlier failure. Controlled TLS
faults remain fatal. Those injected faults validate diagnostics and strict
classification; they do not reproduce or explain the historical #85 failure.

The historical intermittent SSL failure remains unclassified until an
instrumented recurrence establishes its reason and stage. Passing repeated
runs cannot establish that it was harmless. Keep #85 open for that investigation;
no narrower SSL peer-close allowance is justified by this evidence.

## Repeating the complete qualification

With the dedicated backend environment, separate Flight client credentials and
TLS trust configured as described in [the Flight guide](../../v2/FLIGHT_SQL.md):

```sh
for run in 1 2 3 4; do
  python3 v2/qualify_flight.py \
    --dbt /absolute/path/to/dbt \
    --engine-source /absolute/path/to/pinned-engine \
    --server-source /absolute/path/to/flight-source \
    --tls-cert /absolute/path/to/server.crt \
    --tls-key /absolute/path/to/server.key \
    --output-dir "/private/output/issue85-$run" || break
done
python3 -m unittest discover -s v2/tests -v
```

Omitting `--driver-ref` resolves the latest stable release on every invocation.
Retain private logs for diagnosis and review receipts before publishing them.
